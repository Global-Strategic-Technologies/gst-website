# gst_irl_ingestion — prompt companion

> **Audience**: anyone modifying `mcp-server/src/prompts/irl-ingestion.ts` or debugging a live ingestion run.
> **Status**: maintained — update alongside every prompt version bump (version field in the module; history in the conventional-commit log, whose release messages pair prompt + server semver).
> **Reading rule**: this document describes what the prompt _does_. Backlog ids are deliberately kept out of the prose, so nothing here requires you to go look one up; where you need an id for `git` archaeology, the [ledger at the foot](#archaeology) maps them.

## What it does

`gst_irl_ingestion` is the bookend to `gst_information_request_list`: the partner sent the universal intake checklist, the target returned it filled, and this prompt ingests the populated IRL and drives every applicable Hub tool surface in one turn — extracting the 13 diligence dimensions, invoking up to 10 orchestrated tools through per-tool inclusion gates, and synthesizing the outputs into a single partner-level dossier with sections (A)–(K), each tool-backed section closing with a state-carrying Hub deeplink. It is scenario-neutral (buy-side, sell-side, value-creation, post-close); `transactionContext` modulates voice only, never tool selection. One library embed rides along — the decoupled IRL generator source (`gst://irl/source`, the canonical section taxonomy for reconciling minimally-formatted replies). The canonical VDR folder taxonomy is **inlined** as a nine-row table in the body rather than embedded as a whole article, with `gst://library/vdr-structure` kept as a provenance caption; that removed 16.3 KB from every render.

That distinction is what lets `extract-only` forbid every tool in the list above while making one `prepare_irl_body` call: the rule is **no analysis tool invocations**, never "no tool calls", and it is deliberately not weakened to "minimize tool calls".

## Flattened bodies

Some clients — Claude Desktop among them — render each prompt argument as a **single-line input**. Pasting a multi-line markdown IRL into one collapses every newline to a space before the server sees it. Every word survives, in order; the document just becomes one long line.

**This is processed normally.** BL-123 briefly refused it; BL-124 withdrew that a day later on evidence:

- Citation verification calls `normalizeForMatching`, which does `\s+ → ' '` **before** matching — the same transformation the client performed. Flattening cannot change a verdict.
- Nothing else reads line structure. Item enumeration survives on the `- 0-01` prefixes; section headers still match as substrings.
- The hash-bind exists to catch a model **paraphrasing** the IRL. Flattening is not paraphrase.
- The refusal fired at every realistic IRL size and its own remediation could not carry a large body, so operators had no completing path at all.

**What you get instead** is a number: `filledIrl.newlines` in the RUN-AUDIT block, from `serverCachedBodyNewlines` on the envelope. `newlines: 0` on a multi-kilobyte body means the paste was collapsed, and therefore that the body **will not hash-match the file on your disk**. That mismatch is the only real consequence, and explaining it is the entire purpose of the field. It is not an error and nothing acts on it.

One caveat worth knowing: this is benign for the IRL's current bullet-list shape. A markdown **table** or code block would genuinely be destroyed by flattening, and could not be recovered. No IRL contains one today.

## Provenance capping

`irlSource` is what the **model** claims about where the bytes came from. Its evidence for the strongest form — `partner-paste-verbatim-prepop` — was that a `**Body-binding hash:**` directive appeared in the body, and the presence of a string survives export, so a replayed payload carried the same evidence a fresh invocation did.

The server now records what it actually witnessed (`mcp:irl-body-prov:<irlBodyHash>`, first-write-wins, 4 h) and applies a **monotone downgrade**:

| Model asserts | Server record says | Result                                                   |
| ------------- | ------------------ | -------------------------------------------------------- |
| `-prepop`     | `prompt-render`    | unchanged                                                |
| `-prepop`     | `prepare-tool`     | **capped** to `partner-paste-verbatim`, disclosed in (J) |
| `-prepop`     | no record          | unchanged, disclosed in (J) as unverified                |
| anything else | any                | **unchanged**                                            |

**It caps; it never derives.** `prepare-tool` is produced identically by an interactive partner paste relayed through `prepare_irl_body` and by a model reconstruction from an xlsx — the server cannot see the difference. A _derived_ value could therefore never be `model-reconstruction-from-xlsx`, which would hand every reconstruction run a partner-paste grade and sail it past the `requireVerbatimBody` gate that exists to catch exactly that.

Because a cap only ever weakens, and the gate accepts both partner-paste forms, capping never changes a gate outcome — it is visible only as a gap-list entry. An unreadable or unbound store degrades to "cannot verify" rather than failing the run: a missing body corrupts the dossier, a missing provenance record only weakens an audit claim.

## Audit levels

The single most important thing to understand about this prompt: **the audit level is a display axis, never a correctness one.** The provenance chain — body-binding hash, the `validate_irl_provenance` precheck, the `compose_dossier_envelope` composition — runs identically at all three levels. What changes is how much of the resulting evidence appears in the output.

| Level                | (K) footer, per-section fences, citation self-check | Meta JSON fence | `RUN-AUDIT` block |
| -------------------- | --------------------------------------------------- | --------------- | ----------------- |
| `standard` (default) | no                                                  | no              | no                |
| `enhanced`           | **yes**                                             | no              | no                |
| `debug`              | yes                                                 | **yes**         | **yes**           |

`enhanced` is the level whose two thresholds diverge, and therefore the one most easily got wrong: it adds the per-claim provenance surfaces without the run telemetry.

**Enforcement lives in the tool response, not in prompt prose.** `compose_dossier_envelope` omits `metaFenceMarkdown` below `debug` and `provenanceFooterMarkdown` below `enhanced`, and its `emitInstructions` names only the blocks it actually returned. This is load-bearing rather than stylistic: the envelope tool exists _because_ body-text directives were empirically established to read as descriptive context while tool output reads as procedure (see [Server-side enforcement](#server-side-enforcement)). A prompt-body clause saying "do not transcribe this" would have staked the whole feature on the one mechanism already known not to work. The fields are _omitted_, never set to `undefined` — a tool response's text mirror is built with `JSON.stringify`, which drops undefined-valued keys, so an explicit `undefined` would leave the machine and model channels disagreeing about whether the field exists at all.

**Scope: the two gated RENDERED BODIES.** State the rule on the _rendered-body_ axis, not the builder axis and not the mode axis.

The rule used to be builder-phrased, and the reason it was — recorded here because a future reader will otherwise see this doc adopting the phrasing the old wording warned against — is that **mode and rendered body could diverge**: `build()` dispatched on `filledIrl` absence before any mode check, so `{ mode: 'extract-only' }` with no body rendered the _interactive_ builder while `mode === 'extract-only'`, and a mode-phrased rule would have left that case ungated. Closing that gap removed the divergence. `build()` now consults `mode` on both branches, so rendered-body identity **is** the mode axis, and builder identity is the one that no longer tracks it: three builders produce four rendered bodies, because `buildInteractiveBody` has a full arm and an extract-only arm.

The two arms never co-render, so the gate is arm-conditional rather than incoherent. `showRunAudit` / `showAuditDisplay` are computed **inside** the full arm rather than above the branch, so they are _unreachable_ on the extract-only arm rather than merely unused — otherwise the next gated element added to the shared header would silently level-gate extract-only and falsify the exemption below, with no test to catch it.

**Both extract-only bodies are exempt from the gate entirely** and emit their full shape at every level. They produce no partner-facing dossier to keep clean, the `mode` description promises provenance, and downstream automation parses the record and then the meta fence — the record is the artifact, the fence is its run metadata.

**Exempt from gating on the level is not the same as not stating it** (BL-125). Because `extract-only` makes no envelope call, its meta fence is model-authored — so it is the one surface where `auditLevel` reaches the artifact from the model's belief alone, and that belief was measured wrong in three production runs of three. All three builders now **state** their resolved `mode`, `auditLevel` and `transactionContext` in a Run parameters block the model copies rather than infers. `extract-only`'s directive set is still identical at every level; only the stated level differs.

**`requireVerbatimBody` is stated on the one-shot body and the interactive full arm only** — not on either extract-only body. The selection rule is whether the surface has a consumer for the value: neither extract-only body invokes an **analysis** tool (the deferred arm's one call is `prepare_irl_body`, which computes nothing about the target and reads no gate), and the flag is neither a meta-fence key nor a `RUN-AUDIT` field, so stating it there would invite enforcement of a gate that body forbids reaching. Until BL-125 it was stated nowhere at all — fourteen occurrences in `src`, zero render-time readers — which meant the server-side refusal it gates could not fire, because the server reads the flag from the tool input the _model_ supplies.

**Operator consequence**: a `standard` run is a draft. The client-ready gating checklist in [`OPERATOR_RUNBOOK.md`](../../../../src/docs/development/OPERATOR_RUNBOOK.md) reads the `RUN-AUDIT` block, so signoff runs invoke `auditLevel: debug`. A `standard` dossier is not less _verified_ — it is less _evidenced_, and signoff reads the evidence.

## Execution model

**Three builders, four rendered bodies**, dispatched in `build()` on `filledIrl` × `mode`:

| `filledIrl` | `mode`         | Rendered body                                                                                                                    |
| ----------- | -------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| absent      | `full`         | context check, then paste-request only if nothing arrived → full sweep                                                           |
| absent      | `extract-only` | context check, then paste-request only if nothing arrived → `prepare_irl_body` → the extraction procedure (the **deferred** arm) |
| present     | `full`         | one-shot sweep                                                                                                                   |
| present     | `extract-only` | one-shot extraction, copying the render-time `**Body-binding hash:**` directive rather than minting a hash                       |

The two extract-only arms share `extractOnlyProcedureSections()` — the whole procedure from the `## Extraction plan` header through the voice directives, **including** the meta-fence directive and the workbook column contract. Callers therefore do not name the column contract separately; doing so renders it twice.

**Workbook column contract (all bodies)**: the IRL xlsx has seven columns — `A Reference | B Request | C Status | D File Location | E Comments | F Notes | G Response` — and D/E/F carry authored content, not metadata (GST pre-populates research into Comments, sources into File Location, caveats into Notes; the recipient confirms via Status). Each filled row renders as `- <ref> <request> [<STATUS>] — <answer> (Source: <D>) (Note: <F>)`, where `<answer>` is **G and E joined into one contiguous unlabelled span** — a label between them breaks citations that read across the boundary. Source and Note stay **outside** the answer slot, so a row carrying only a filename renders `— <NO RESPONSE> (Source: …)` and cannot open a gate. The contract also warns the model to trust the data sheet's header row rather than the Instructions sheet (workbooks in the wild document a stale five-column layout), and states the citation-hygiene rule: cite from the answer slot only, never from `(Source:)` / `(Note:)` — both are inside the verifier's haystack, so a filename citation verifies and raises no gap. Rationale and the accepted residual: [ADR-0015](../../../../src/docs/adr/0015-irl-canonical-body-reads-full-workbook.md). The operator-side `npm run irl:extract` emits this same shape.

**Fill-ratio pre-flight (blocking, before any extraction)**: walk the 10 canonical IRL sections (00–09; optional 10/11 excluded), compute `fillRatio = substantiveCells / totalResponseCells` over the **composed answer span** (Response + Comments), composing before counting. `< 15%` → HALT with a wrong-IRL warning, emit only (A). `15–40%` → proceed with partial-IRL framing and tightened elision (any tool whose source sections are all empty is skipped, surfaced in (J)). `≥ 40%` → proceed normally. The ratio is the first sentence of (A) in all paths.

**Inclusion gates** (evaluated per tool; failures are elided with a (J) entry): `generate_diligence_agenda`, `assess_infrastructure_cost_governance`, and `search_radar` always pass; `compute_techpar` requires ARR (Section 00) AND an eng-cost or hosting signal (02/03); `estimate_tech_debt_cost` requires ≥ 1 Section 04 row with a substantive answer (a file pointer or a caveat is not signal); `search_regulations` requires a Section 09 framework OR a fired EU-AI-Act / NIS2 conditional trigger; `search_portfolio` requires a Section 00/01 product-or-industry signal; the two facet tools inherit from their search siblings.

**Meta JSON fence** — 13 keys: `promptName`, `promptVersion` (server-overridden from the prompt registry), `modelVersion`, `mode`, `auditLevel`, `transactionContext`, `fixtureFillRatio` + `fixtureFillRatioStatus` (both server-derived from `substantiveCells` / `totalCells`; see BL-130) (`ok`/`partial`/`halt`), `gatesPassed`, `gatesElided` (`{tool, reason}`), `conditionalTriggersFired` (`EU_AI_ACT`/`NIS2` only), `defaultFiredFrameworks`, `forceToolsApplied`. It has **two provenances**: server-rendered wherever an envelope call happens, and model-authored in `extract-only`, which makes no envelope call at all. That is why the template in the prompt body has to be maintained in lockstep with `renderMetaFence`. In `extract-only` it is the **run-metadata** fence and a sibling of the extract record's `_meta` — the record self-describes the travelling artifact, the fence describes the run — and both take `promptVersion` from the same Run-parameters bullet, which is that mode's only source for it.

**Output sections**: (meta fence, `debug` only) → **(A)** target snapshot → **(B)** diligence agenda → **(C)** TechPar → **(D)** ICG → **(E)** tech debt → **(F)** regulatory exposure (one subsection + one deeplink per framework) → **(G)** comparable engagements → **(H)** market signal → **(I)** synthesis/handoff memo → **(J)** gap list (always emitted; six model-supplied categories plus server-appended `provenance-gap`/`tier-mismatch`/`tier-fabrication`/`map-absent`) → **(K)** provenance footer (`enhanced` and above). `enhanced` also emits an `audit: <letter>` JSON fence + self-check after each of (C)–(H). The mid-sweep tool-error degradation rule applies at every level (verbatim error, section marked extraction-only, sweep continues; halt only if the agenda prerequisite fails).

**Envelope chain (full mode, every level)**: converge citations on `validate_irl_provenance` first — cheap iteration until ≥ 0.90 verified or 4 rounds, with array-form citations for genuinely multi-bullet claims — then call `compose_dossier_envelope` ONCE. It returns the markdown blocks the audit level calls for. The IRL body travels by hash, not bytes: one-shot mode pre-populates the server body cache at prompt-render time and embeds a `**Body-binding hash:**` directive the model copies as `irlBodyHash` (`irlSource: partner-paste-verbatim-prepop`); interactive mode routes through `prepare_irl_body` (`Bl076BodyCacheMissError` on skip). The body is **not** a public input on the envelope tool — passing it would silently re-incur the whole-body emission cost the cache exists to remove, since unknown keys are stripped rather than rejected.

**Extract-only** runs the same pre-flight, gates, and `_audit` discipline, and invokes **no analysis tool** — its one call is `prepare_irl_body`, and only on the deferred arm. It emits, in order: a `record: irl-extract` fence (the primary artifact), a `worksheet: generate_diligence_agenda` fence, one `payload: <tool>` fence per gate-passing tool, `elided: <tool>` fences for failures, (J), (K), and the run-audit block — no dossier prose, no deeplinks, no envelope.

### The IRL extract record

The mode's primary output, and the reason the mode exists. One JSON document describing **the target**, keyed by the canonical IRL taxonomy, covering every answered row. The `payload:` fences stay and are demoted to a **derived projection** of it — they are consumer-shaped by design, which is exactly why they could not serve as the artifact.

Per fact: the workbook `Reference` verbatim (`0-03`, _not_ the `NN-II` exclusion key `list_irl_requests` returns — `_meta.refFormat` names which vocabulary is in play), the **verbatim IRL request text** (what a consumer matches on, so there is no lookup step and no mapping table to keep in sync), the workbook `Status`, a verbatim answer-slot excerpt capped at 240 characters with word-boundary truncation and an `excerptTruncated` flag, an optional normalized scalar with its conversion basis, and an extraction-side tier.

`_meta` dates and versions the artifact itself — `generatedAt`, `generatedAtSource`, `promptVersion`, `irlBodyHash`, `irlSource`, `excerptCapChars`, `coverage` — because it is context-borne and nothing server-side can supply any of that later. Schema and the body directive both live in `src/schemas/irl-extract-record.ts`, interpolating the same constants so prose and validation cannot state different numbers. Decisions: [ADR-0019](../../../../src/docs/adr/0019-irl-extract-record-subject-indexing.md).

**Provenance.** The deferred arm calls `prepare_irl_body` once after the paste — it computes nothing about the target; it mints the hash and the provenance record the travelling artifact needs — and copies the returned `mintedAt` into `_meta.generatedAt` with `generatedAtSource: server-witnessed`. That value is the **stored** one (the store is first-write-wins), so a repeat call inside the 4 h window returns the original mint time; when no record landed the field is absent and the model falls back to `model-asserted`. The one-shot arm copies the render-time prepop's binding hash instead — the stronger grade — and its `generatedAt` is `model-asserted`, because that witness exists but is unreachable in-band (the registry discards the handler result).

### Cross-session posture — what a record meets in session 2

The record travels in context; the body cache behind `_meta.irlBodyHash` does not. In a later session that hash **no longer resolves**, and `validate_irl_provenance` in its hash form **fails** with `cache-miss` — it does not degrade to per-citation verdicts. Two branches, neither depending on hash equality:

- **Primary — re-seed, then validate by hash.** Call `prepare_irl_body` with the paired body once, then `validate_irl_provenance` with the hash. Primary because the body-direct (`filledIrl`) form re-emits the whole body per call — the production damage recorded in `validate-irl-provenance.ts` (a 50 KB body emitted twice per precheck iteration, ~12 % byte loss) — and real bodies run 60–80 KB, above the emission ceiling ([ADR-0003](../../../../src/docs/adr/0003-irl-xlsx-canonicalization-hash-bind.md)). **Body-direct is the small-body fallback, not the lead.**
- **Hash equality attests IDENTITY, not verifiability.** Hashing is byte-for-byte with no normalization, and paste paths can legitimately alter bytes (the BL-124 flattened-paste case). Hand-computing is forbidden by `prepare_irl_body`'s own contract, so the session-2 hash comes from **that tool's result** and is compared against `_meta.irlBodyHash`. Equal → the exact body the record was extracted from. Different → verification still runs against the supplied bytes, and the output must disclose that the body is not byte-identical to the record's minted source. The byte-reproducible producer is the operator-local `npm run irl:extract` over the same workbook, not a re-paste.

The record and the filled IRL therefore **travel together as a pair when full provenance matters**. A record alone still resolves a consumer's inputs, with its citations carried as asserted-not-verified — which is the distinction `irlEvidencePrecedence()` makes every consumer state.

## Server-side enforcement

The original theory was body-level coaching. It failed empirically: three body-rewrite rounds against a real client IRL (June 2026) showed the model treats body directives as descriptive context, not procedure — currency, headcount-scope, dataSensitivity, and MTTR-OPEN clauses were all skipped. Enforcement pivoted to the tool seam: a required `_audit` sibling on each tool's input schema, with cross-field refinements run in the handler body (plain `ZodObject` only — the MCP SDK publishes an empty schema for unions/`ZodEffects`) that reject with a structured diagnostic the model retries against. **That finding is also why the audit levels are enforced in the tool response rather than in prose.** Per-tool families, as implemented in `mcp-server/src/schemas/`:

- **`diligence-audit.ts`** (`generate_diligence_agenda`): per-dimension `tier` (`1`/`2`/`3`) + `citation` matching `Section NN — <substantial excerpt>`; tier↔value coupling (tier 3 ⇔ `unknown`, both directions rejected otherwise); `revenueRange` currency normalization (`nativeCurrency` enum + `currencyConversion {nativeAmountMillions, usdRate, convertedUsdMillions}` with bracket cross-check); `headcount.scope` must be `engineering-only` for non-unknown values; `dataSensitivity.piiCategoriesPresent` bucket cross-check (e.g., `low` incompatible with PHI/PCI); `growthStage.velocityEvidence` enum.
- **`techpar-audit.ts`** (`compute_techpar`): single declared `monetaryBasis` (currency + conversionRate) across all money fields, plus per-monetary-field `annualizationSource` (`irl-annualized-stated` | `monthly-x12` | `ytd-annualized-with-period` — requires `ytdMonths` 1–11 + a `ytdMathCheck` arithmetic-consistency block | `estimated-from-headcount` | `estimated-from-anchor`). This closed the observed cross-run swings (9.1%/13.9%/31.2% R&D% on the same fixture from ad-hoc annualization).
- **`tech-debt-audit.ts`** (`estimate_tech_debt_cost`): `mttrSource`/`incidentsSource` enums (`irl-stated` | `irl-open` | `irl-absent` | `irl-scope-mismatch`); any non-`irl-stated` source REQUIRES the value be `null` (placeholder substitution structurally impossible); nulled fields are elided from the engine and returned in `extractionOnly: [...]`, which the dossier renders as extraction-only with a (J) follow-up.

Two later layers extend the same pattern at the envelope seam: **derived-tier discipline** — `deriveTier()` computes effective tier from citation properties (verbatim substring → tier 1; `Section --` sentinel → partner-supplied; neither → `tier-fabrication` gap), so model-declared tier is a hint, not authority (see [ADR-0003](../../../../src/docs/adr/0003-irl-xlsx-canonicalization-hash-bind.md)) — and **body-by-hash**, where the IRL body is server-cached and re-hydrated by `irlBodyHash` with a sha256 bind check, never round-tripping through model emission (see [ADR-0002](../../../../src/docs/adr/0002-irl-body-by-hash-cache.md)). The envelope also enforces `defaultFiredFrameworks` at the schema seam: partition vs. `conditionalTriggers.fired`, certification-scope rejection, and Hub-backing auto-degrade to `map-absent:` gaps.

A third layer is **derivation rather than enforcement** (BL-130, server 0.55.0): `fillRatio.percent` and `.status` are pure functions of `substantiveCells` / `totalCells`, so the envelope recomputes them — rounding to the nearest integer first, because the pre-flight directive applies the halt/partial/ok thresholds to the rounded value, and a raw-ratio check would flag a run at 39.6% that correctly reported `40 / ok`. The derived values govern the meta fence; a disagreement beyond 1 percentage point, or on status, is disclosed as a `provenance-gap:` entry directing a section (A) restatement. It is a disclosure, not a rejection — and where `substantiveCells > totalCells` no percentage can be derived at all, so the caller's range-checked values are kept and the inconsistency is surfaced instead. This is the one place the pattern **derives** rather than **caps**, and [ADR-0018](../../../../src/docs/adr/0018-body-integrity-and-capped-provenance.md) records why the two are not in conflict.

## Provenance & audit surface

At `auditLevel: debug`, every body shape mandates a closing **`RUN-AUDIT`** fenced YAML block — the operator's single-surface run audit. It carries: `promptVersion`; `runScenario`; `filledIrl` (bytes / `source` enum including `partner-paste-verbatim-prepop` and an honest `placeholder` option / 120-char head+tail fingerprints); `firstEnvelopeCall` (`irlBodyHash`, `hashBindResult`, `provenanceVerification` counts incl. `tierMismatches`/`tierFabrications`); `precheck` (iterations / attemptsTotal / outcome / errorsEncountered); `countersScope` + `toolCallCounts` — both copied VERBATIM from the envelope output, since model self-narration demonstrably drifted and the server counts are ground truth; `toolErrors` (per-attempt diagnostics, strict partition from precheck errors, arithmetic-checked against the counts); envelope-call cumulatives + `meaningfulRecallsHaveDifferentInputs`; `conditionalTriggers` (considered/fired/suppressedWithRationale/defaultFiredFrameworks); structured `gatesElided`; and `response` (continuations, block emission point, `compactionEvents` with null-preferred-over-false-zero semantics).

**`countersScope` states how far back the counter snapshot reaches**, and therefore whether the derivation identities are checkable at all: `session` (stdio — one process, one counter map, whole session), `run` (remote + the durable run-scoped store read successfully — every call against this IRL body, across requests, for a 4-hour window, keyed by the body rather than by the invocation), `request` (remote with no readable store — only the envelope call's own request; earlier calls are legitimately absent, and the model is told to leave the gap visible rather than close it). The identities are stated conditionally on that value, and `attemptsTotal === attempted` is replaced by a reconciliation subtracting the transport-classed `errorsEncountered` entries — durable writes land at wrapper exit, so an attempt that never reached the server was never countable. See [ADR-0016](../../../../src/docs/adr/0016-run-scoped-durable-tool-call-counters.md).

`hashBindResult` semantics are load-bearing: **`pass-bound`** means the hash was copied from a server-emitted `**Body-binding hash:**` directive (one-shot mode — the bind is to partner-authoritative bytes; high audit grade); **`pass-internal`** means no directive existed (interactive mode) and the model self-computed the hash — honest internal consistency only, medium audit grade. Reporting `pass-bound` without a directive to copy from is a fabricated audit claim.

## Arrival routes

The filled IRL can reach a run three ways, and the prompt supports all three. They differ in
what the SERVER can witness, not in how much work the operator does.

| Route                                          | `runScenario`         | `irlSource`                      | `hashBindResult` |
| ---------------------------------------------- | --------------------- | -------------------------------- | ---------------- |
| `filledIrl` prompt argument                    | `partner-paste`       | `partner-paste-verbatim-prepop`  | `pass-bound`     |
| Attached `.md`, or a chat paste                | `partner-paste`       | `partner-paste-verbatim`         | `pass-internal`  |
| Attached `.xlsx` (model composes the markdown) | `xlsx-reconstruction` | `model-reconstruction-from-xlsx` | `pass-internal`  |

**`irlSource` grades WHO AUTHORED the bytes, not how they arrived.** A partner-authored `.md`
is `partner-paste-verbatim` whether it was pasted or attached; the server cannot tell those
apart (see the capping section above) and no honest grade distinguishes them. A workbook you
parsed is a reconstruction however clean the composition.

**Two gates, two axes — do not conflate them.**

- `requireVerbatimBody` asks _"did a model reconstruct this?"_ All three partner-authored
  routes pass; `model-reconstruction-*` and `placeholder` are refused.
- `hashBindResult: pass-bound` asks _"is the hash server-emitted?"_ Only the argument route
  produces it, because only there does the server hash the body itself at render time.

So an attachment run can pass the verbatim gate and still not be client-ready: the
[operator runbook](../../../../src/docs/development/OPERATOR_RUNBOOK.md) requires `pass-bound`
for a client-facing deliverable, and that means the argument route. Drafting and extraction
runs have no such requirement.

**What the model is asked to do about it.** Step 1 checks context before asking, so an
operator who attached the file is not asked to paste it again. Two branches keep that safe: an
attachment the model cannot actually read (a filename only, or a flattened extraction with the
column structure destroyed) sends it back to a paste request rather than a reconstruction, and
multiple candidates in context are named rather than merged.
