# ADR-0009: Compliance-grade audit log — hash-chained, R2-immutable, Upstash-sequenced

- **Status**: Accepted (2026-07-26)
- **Source initiative**: BL-033 Slice 3a (external-pilot audit logging; the BL-033 stanza in [`../development/BACKLOG.md`](../development/BACKLOG.md) remains the open initiative tracker — this slice closes the **emission + durable-store** half of its Audit-logging AC block, deferring signed-URL export, the quarterly integrity-check automation, and the `?audit_full_payload=true` retention flag)

## Context

BL-033 makes the MCP server a product a PE firm's compliance team can trust. Its Audit-logging AC block (`../development/BACKLOG.md:260-267`) requires every tool invocation written to an **append-only, tamper-evident** store — full input parameters, GDPR-truncated caller IP, timestamps, duration, outcome — shipped to a store that is explicitly **"never the same Sentry/Cloudflare logs used for ops,"** with a SHA-256 hash chain and 7-year (SEC 17a-4) retention. This is the compliance moat itself.

Two forces shaped the design. **(1)** The existing observability path (`src/metrics/` → Analytics Engine) is deliberately unsuited: `MetricSink.write` is sync + non-throwing + AE-projected (16 KB blob caps, 3-month retention, and it feeds the ops Sentry/CF-logs surface the AC forbids). Audit needs full input params off that surface entirely. **(2)** A linear hash chain requires a single writer over a strict total order, but the durable pipeline the reference architecture specifies (`../development/BACKLOG.md:312-321`) is Worker → **Cloudflare Queue** → consumer → **R2** — an at-least-once queue with batch redelivery and no cross-store transaction. R2 and Cloudflare Queues did not exist anywhere in this repo before this slice; both are first-of-kind bindings the operator provisions.

## Decision

**A separate audit path, co-located on the existing chokepoint.** `withMetricsCore` (`mcp-server/src/metrics/with-metrics.ts`) already wraps every tool handler with `{name, args[0], result, duration, outcome, keyOwner}` in scope. We thread a new `AuditContext` (`{sink, requestId, ipPrefix, keyOwner}`) alongside the metrics sink and, for `tool_invocation` only, build a full `AuditEntry` (incl. `inputParams` + `outputBytes`) and hand it to a fire-and-forget `AuditSink` — a path wholly separate from `emit()`/`MetricSink`, so input params never reach AE/Sentry/CF logs. (Gated to tools this slice; resource/prompt arg shapes differ — a one-line widening later.)

**Best-effort enqueue, with an honest loss window.** `QueueAuditSink.write` hands `env.AUDIT_QUEUE.send(entry)` (with one in-promise retry) to `ctx.waitUntil` — off the request latency path, non-throwing, matching the house "emission never breaks a tool call" contract. Durability is the Queue's job (at-least-once + consumer retry + DLQ) **for records the Queue accepted**; the enqueue hop itself has a residual loss window (send rejects both attempts, or the isolate is evicted before the queued `waitUntil` runs). This is a deliberate _pilot_ posture — we do not ratify a guaranteed-capture SLA no client has contracted. **Rejected (for now): fail-closed.** The concrete revisit trigger + seam: a per-client `guaranteedCapture` flag (off the OAuth client record, same seam as the deferred `?audit_full_payload=true`) would route through an awaitable `AuditSink.writeAndAwait(entry)` (already reserved on the interface) that `withMetricsCore` awaits **before returning the tool result**. Not built now.

**Crash-safe hash chain via an `entryId→seq` ledger + atomic Upstash `MULTI`; R2 an idempotent projection.** The queue consumer (`src/audit/consumer.ts`, the Worker's `queue` handler) is a single writer (`max_concurrency = 1` + a belt-and-suspenders single-flight lock). Per batch:

1. Read the chain tip `{lastSeq, lastHash}` from Upstash (key `mcp:audit:chain-tip:<env>`).
2. For each message, reuse `seqOf:<entryId>` if present (sequenced by a prior, possibly-crashed attempt); otherwise it is FRESH.
3. FRESH entries are sorted by `entryId` (deterministic, **independent of arrival order / batch composition**) and assigned `seq = lastSeq+1..`, chaining `entryHash = SHA-256(prevHash + canonicalize(entry))` (first from `lastHash`, rest in-memory).
4. **One atomic `redis.multi()…exec()`** commits every FRESH `seqOf:<entryId> = {seq, prevHash, entryHash}` **and** the advanced tip — all-or-nothing.
5. **Project every** batch entry (FRESH + already-sequenced) to R2 at `audit/<env>/<yyyy>/<mm>/<dd>/<paddedSeq(16)>.json` with `onlyIf: { etagDoesNotMatch: '*' }` — an existing object makes `put()` return `null` (= "already durable"), not an error.
6. `ackAll` only on a fully durable commit; **any** failure (including a null/unreachable Upstash) `retryAll`s the whole batch and surfaces to Sentry.

**Why consumer-assigned `seq` is the canonical order, not the wall-clock `tsIso`:** queue delivery order ≠ production order, so the chain cannot key on time; `tsIso` is recorded as data. **Why an entry never forks or shifts on redelivery:** the invariant `seqOf exists ⟺ its seq+tip were committed in a MULTI` holds because they commit atomically — an un-sequenced entry means the MULTI never ran (nothing durable), so re-sequencing is free; a sequenced entry keeps its seq forever and is merely re-projected. A recomposed redelivered batch (old uncommitted + new entries) therefore cannot fork: already-sequenced entries keep their seq, new ones append after the current tip.

**Rejected alternatives:**

- **Piggyback on `MetricSink`/AE** — sync + non-throwing + 16 KB-capped + ops-surface; cannot carry full params and violates "never to ops logs."
- **Chain tip / ledger in Workers KV** (the OAuth substrate) — KV is _eventually_ consistent, so a stale `lastHash` read could fork the chain, **and** KV has no multi-key transaction, so it cannot commit `seqOf`+tip atomically. Upstash gives read-after-write consistency + `MULTI`, and already backs this repo's locks/counters. (Assumption to hold: the `gst-mcp` Upstash DB has no read-replica/global-read-region routing that weakens read-after-write.)
- **Object-per-batch NDJSON** — the arrival-assigned seq range in the key shifts under batch recomposition on redelivery and collides under `If-None-Match`. Object-per-entry keyed by the stable `seq` is idempotent and collision-free; pilot volume is low/intermittent so PUT count is a non-issue.
- **Fail-closed capture now** — converts a transient Queue/isolate hiccup into a client-facing outage for a guarantee no pilot has contracted (see revisit trigger above).

## Consequences

- **Code that cites this decision**: `mcp-server/src/audit/{entry,redaction,audit-sink,consumer}.ts`, the `withMetricsCore` audit branch + `MetricsContext.audit` (`src/metrics/with-metrics.ts`), the `AuditContext` threading (`src/server.ts`, `src/pipeline/handle-authenticated.ts`), `Env` + the `queue` handler (`src/worker.ts`), the `audit_batch` metric event (`src/metrics/_schema.ts`), and the `wrangler.toml` Queue/R2 blocks. Operator runbook: [`../../../mcp-server/src/docs/operations/AUDIT_LOG.md`](../../../mcp-server/src/docs/operations/AUDIT_LOG.md). System reference: `mcp-server/src/docs/ARCHITECTURE.md` § Audit logging.
- **Accepted trade-offs / operational edges**: (a) the best-effort enqueue loss window above — a first-hop drop leaves a `seq` gap the deferred integrity check surfaces (as does a DLQ'd batch); (b) `seqOf:`/`hashOf:` ledger keys accumulate in the shared `gst-mcp` Upstash DB over the 7-yr horizon — `seqOf:` should carry a TTL longer than max queue retention (redelivery beyond that is impossible), and a `hashOf:` compaction window is a follow-up if that key is later split out (this slice stores the hash inside `seqOf` and needs no separate `hashOf`); (c) `newRequestId` mints its own UUID rather than reusing `cf-ray` — portable across stdio/tests and stable per logical request across retries.
- **Compatibility**: net-new bindings (no migration). The operator MUST provision each env's Queue + DLQ + R2 bucket (with a **Bucket Lock** rule — Cloudflare's retention/immutability feature; versioning is not needed given create-only writes — at 7-yr retention) **before** the Worker deploys — a `[[queues.consumers]]` referencing a missing queue fails `wrangler deploy`, and staging auto-deploys on merge. Steps in AUDIT_LOG.md.
- **Revisit triggers**: a pilot client contractually requiring guaranteed capture → build the fail-closed `writeAndAwait` seam; a client requiring full output-payload retention → the `?audit_full_payload=true` flag; quarterly compliance attestation → the integrity-check automation + signed-URL export (the deferred slice, which re-walks the chain the R2 objects already carry).
