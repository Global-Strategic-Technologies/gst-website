# ADR-0008: OAuth 2.1 as an embedded authorization server on the MCP Worker

- **Status**: Accepted (2026-07-24)
- **Source initiative**: BL-033 Slice 2 (external-pilot auth; the BL-033 stanza in [`../development/BACKLOG.md`](../development/BACKLOG.md) remains the open initiative tracker — this slice closes its Authentication & authorization AC block)

## Context

The MCP Worker authenticated exclusively via static `MCP_KEY_*` Wrangler secrets — right-sized for an internal team of <10 (ADR-worthy reasoning recorded at the time in `mcp-server/src/docs/ARCHITECTURE.md` § Bearer-token auth), but wrong for external client onboarding: no per-client identity, no consent semantics, no standard flow a stranger's client can discover. The MCP spec (2025-11-25 revision) defines the auth model — the MCP server as an OAuth 2.1 **resource server** (RFC 9728 protected-resource metadata MUST, PKCE S256 mandatory, RFC 8707 audience validation, DCR demoted to MAY with pre-registration + CIMD preferred) — and Claude's native Connectors UI requires OAuth, which the bearer-only Worker could not satisfy (the team used the `mcp-remote` bridge workaround documented in `REMOTE_CLIENT_SETUP.md`).

Three hard constraints shaped the decision: (1) three static-token consumers (website `RadarFeed.astro`, the latency probe, bridge users) must keep working unchanged; (2) tool-level scope semantics (`tool:radar:*` gating) are central to the BL-033 ACs and must stay ours; (3) per the operator's build-capability-don't-tune directive, the solution must carry zero per-seat cost for hypothetical future users.

## Decision

The Worker becomes its **own OAuth 2.1 authorization server** via `@cloudflare/workers-oauth-provider` (pinned exact at 0.8.2), mounted as a **sub-router** from `worker.ts` — never `export default`-wrapped — with dual cheap-first validation on API routes: static `MCP_KEY_*` scan (constant-time, zero I/O, byte-identical legacy path) → `mcp_m2m_*` local JWT verify → provider token validation. `auth.failed` telemetry fires only after every path fails.

Load-bearing choices:

- **Identity = delegation over the existing key roster.** The consent page authenticates the human via their existing `MCP_KEY_*` value (same constant-time `matchToken` core as the header path); grants carry `keyOwner OAUTH:<owner>` and scopes bounded by the key's scopes. No new user directory.
- **Scope strings are the existing catalog verbatim** (`src/auth/scopes.ts`) — OAuth tokens flow through the same `hasScope`/`assertScope` machinery as bearer keys; the `AuthSuccess` contract is the seam, and the whole post-auth pipeline (`pipeline/handle-authenticated.ts`) is shared by all three auth paths.
- **DCR disabled; pre-registration + CIMD instead** — matching both the BL-033 AC and the spec's direction; admin endpoints (`MCP_ADMIN_KEY`-gated) create clients via the library's `createClient`.
- **M2M client_credentials is our own token-endpoint branch** (`oauth/m2m-token.ts`) issuing **self-contained HS256 JWTs** (1h, audience-bound, no refresh token), because (a) the library has no client_credentials grant (verified against the 0.8.2 types), and (b) KV-opaque tokens would hit KV's ~60s cross-colo eventual consistency on mint-then-immediately-use. Client auth: RFC 7523 `private_key_jwt` (preferred; ES256 vs inline JWKS, ≤5-min assertions, jti one-shot) or hashed-secret compare.
- **Consent nonces live in OAUTH_KV, not Upstash** (deviation from the implementation plan's original mirror-the-admin-reauth detail): one substrate for all OAuth state, consent survives an Upstash outage, and miniflare KV makes the full flow integration-testable. Trade-off: KV get+delete is not atomic, so the server-side one-shot has a small replay window — accepted because the double-submit HttpOnly cookie is the primary CSRF defense.

**Rejected alternatives**: _Cloudflare Access for SaaS as the AS_ (the original backlog recommendation, re-evaluated 2026-07-23 with fresh research: identity-shaped rather than per-tool scope semantics, Zero Trust per-seat cost for external users past 50, dashboard-coupled config); _external IdP (Auth0/WorkOS/Clerk)_ (third vendor in the auth path, cost, and the scope model would still be ours to build); _hand-rolled AS_ ("OAuth is easy to implement insecurely" — the backlog's own risk register); _wrap-everything `export default oauthProvider`_ (library would shape 401s/CORS for static-key traffic, breaking the legacy contract and taking routing control from the pre-auth pipeline); _`resolveExternalToken` for static keys_ (same response-shaping objection); _KV-stored opaque M2M tokens_ (consistency, above).

**Deferred with re-engage triggers**: _Cloudflare Access as upstream IdP_ — when a real user directory/SSO story is needed (≈>20 external humans or an enterprise pilot demanding SSO); _Enterprise Managed Authorization (ID-JAG)_ — when a pilot client on Okta/Entra asks for zero-touch connector provisioning (the library ships experimental support); _DCR_ — only if the spec re-elevates it or a mandatory client supports neither pre-registration nor CIMD.

## Consequences

- **Surfaces added**: `/authorize` (consent), `/token` (library grants + our client_credentials branch), `/.well-known/oauth-authorization-server` + `/.well-known/oauth-protected-resource`, `/oauth/introspect` (RFC 7662, admin-gated, with the M2M revocation cross-check), `/admin/oauth/clients*` + `/admin/oauth/m2m-clients*`. 401s on token-present failures now carry the RFC 9728 `resource_metadata` pointer.
- **New infrastructure**: `OAUTH_KV` namespaces (staging + production), `OAUTH_M2M_SIGNING_KEY` secret, the `global_fetch_strictly_public` compatibility flag (SSRF defense for CIMD's fetch of client-supplied metadata URLs — the flag's purpose, not an incidental toggle).
- **Accepted trade-offs**: the library's refresh rotation briefly holds two valid refresh tokens (documented upstream compromise); M2M revocation is client-record deletion (blocks re-issuance; ≤1h token residual — introspection reports revoked-inactive; emergency = rotate the signing key, killing all M2M tokens); `completeAuthorization` revokes prior grants per user+client (re-consent replaces old tokens — pinned by integration test); the consent nonce non-atomicity above; introspection of library tokens depends on the pinned library version's `unwrapToken` helper.
- **Operational notes**: a newly onboarded `OAUTH:<user>` / `M2M:<name>` keyOwner has no trailing 7-day mean, so its first busy hour above the traffic-spike floor can fire the ticket alert once — expected onboarding behavior (AUTH.md runbook). Under `unstable_dev`, the Worker's request origin is the wrangler.toml route hostname, not the local address (matters for audience-bound tests).
- **Code/docs that carry this decision**: `mcp-server/src/oauth/*`, `mcp-server/src/pipeline/handle-authenticated.ts`, `mcp-server/src/admin/oauth-clients.ts`, `ARCHITECTURE.md` § Auth, `operations/AUTH.md` (runbooks), `operations/REMOTE_CLIENT_SETUP.md` (native Connectors path), integration suites `tests/integration/oauth-*.test.ts`.
