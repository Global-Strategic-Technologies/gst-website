# ADR-0030: The website's locale model is `language[-REGION]`, resolved exact → language → default, served from one template per route

- **Status**: Accepted 2026-09-05 (BL-153 Phases 0–3 landed the same day: foundation, all eight Tier A pages, the switcher and the first-visit band; `es` and `pt-BR` were flipped **live** the same day by operator decision, ahead of native-speaker review, which remains owed); revisit triggers extended 2026-09-27 (translated slugs, automatic redirects), carried over from the BL-153 stanza; **amended 2026-10-24** (BL-153 Slice 3 — Tier B routes, TechPar the first, and the display-currency rule; see the amendment below)
- **Source initiative**: BL-153 — [BACKLOG.md § BL-153](../development/BACKLOG.md#bl-153-website-localization--spanish-and-brazilian-portuguese-on-an-architecture-that-can-carry-dialects-and-regions-later); design hand-off at [LOCALIZATION_HANDOFF_BL-153.md](../development/LOCALIZATION_HANDOFF_BL-153.md); maintained how-to at [LOCALIZATION.md](../development/LOCALIZATION.md)

## Context

The site was English-only with the language hardcoded in three places: `<html lang="en">` in `BaseLayout.astro`, `ogLocale = 'en_US'` in `SEO.astro`, and an English slug→name map in `src/utils/breadcrumbs.ts`. BL-153 adds Spanish and Brazilian Portuguese now and must not need a rebuild when a dialect (`pt-PT`, `es-MX`) or a region preference (currency, units) arrives later.

Constraints that shaped the design, all verified on the branch before Phase 1:

- **Astro 7.2.9 built-in i18n** (`i18n.locales` as `{ path, codes }`, `prefixDefaultLocale: false`) serves root `src/pages/*` as the default locale and `src/pages/[locale]/…` as the others. A **Phase 0 routing spike** (2026-09-05) confirmed: `dist/es/index.html` and `dist/pt/about/index.html` build from one catch-all `[locale]/[...route].astro`; `Astro.currentLocale` inside it is the **code** (`pt-BR`), not the path segment (`pt-br` at the time of the spike, `pt` now), and is `en` on a root page; root static routes keep winning at `/about/`. The default locale needs a non-empty `path` (`'en'`) — an empty one breaks `computeCurrentLocale` in `astro/dist/i18n/utils.js` and is meaningless as a sitemap key.
- **Tests read page source by path.** `tests/integration/mcp-marketing-parity.test.ts` scans `src/pages/hub/mcp/index.astro`; `tests/unit/indexability.test.ts` discovers `noindex` pages by walking `src/pages` and pins `noindex={noindex}` in `BaseLayout` and the robots ternary in `SEO.astro`. Route files therefore cannot move.
- **`astro.config.mjs` imports the registry in plain Node**, before Astro exists — so `src/i18n/locales.ts` must be pure TS (no `astro:*`, no `import.meta.env`), which is why the liveness override reads `process.env` under a recorded exception to the `no-restricted-properties` rule (DEVELOPER_TOOLING § Environment variables).
- **The brand face covers the glyphs.** `fontkitten` (Astro's transitive font parser, no new dependency) opened `public/fonts/gst-mono-var-latin-v1.woff2` (Geist Mono, 410 glyphs) and reported every one of `ã õ ç ñ ¿ ¡ á é í ó ú ü ê ô` plus their capitals and `à â` present — 30 code points, none missing. No `latin-ext` build is needed.
- **Vercel serves one static `404.html`** and cannot know a locale.

## Decision

1. **Locale = `language[-REGION]`**, one registry entry each (`src/i18n/locales.ts`): `code`, URL `path`, `htmlLang`, `ogLocale`, `intl` tag, native `name`, two-letter `short`, `status`. **Resolution is exact → language → default**, applied per candidate when a list (`navigator.languages`) is given: `pt-PT` resolves to `pt-BR` today and to a future `pt-PT` entry with no code change. A dialect is a new row. **Region as a preference is a separate axis** that never selects a catalog; when it arrives it gets its own storage key, not a field inside `gstLang`.
2. **Routing**: Astro built-in i18n, English unprefixed, `/es/…`, `/pt/…`, English slugs. **No `fallback`** — a locale launches whole at Tier A or not at all; serving English under `/es/` would mint duplicate-content URLs.
3. **`status: 'draft' | 'live'`**. A draft locale builds and is reachable by URL (translation review on preview deploys) but is `noindex`, out of the sitemap, emits **no hreflang** (a draft→English link would be non-reciprocal and discarded), and is offered by neither the switcher nor the band. With zero live alternates the switcher and band render nothing, so a site whose translations are all parked as `draft` is byte-identical to its pre-BL-153 form (`es` and `pt-BR` went live on 2026-09-05, so production renders both controls). `PUBLIC_I18N_LIVE_LOCALES=es,pt-BR` forces liveness for test runs regardless of the registry (a build/dev-server input only; page scripts never read it).
4. **One template per route.** Bodies live in `src/page-templates/<Name>Page.astro` taking `locale`; root route files become wrappers that render the template with `DEFAULT_LOCALE` (paths preserved for the source-scanning tests). Non-default locales come from **one catch-all**, `src/pages/[locale]/[...route].astro`, whose `getStaticPaths` is `nonDefaultLocales() × TIER_A_ROUTES` (`src/i18n/routes.ts`), with the template map in `src/page-templates/registry.ts` because `getStaticPaths` sees imports but not frontmatter locals. Adding a page to every locale = one registry row + one template entry. _Deviation from the stanza's per-route `[locale]/about.astro` files, chosen on the spike's evidence._
5. **Catalogs**: `src/i18n/<locale>/<namespace>.json`, flat dot-keys, plain strings; English is the schema and `useTranslations(locale, ns).t(key)` is typed from it. Markup-bearing strings go through `tHtml()` with a tag allowlist (`a strong em br code`, plus `p` for multi-paragraph FAQ answers). Staleness via sidecars `<ns>.source.json` (key → sha256-8 of the English string at translation time), written by `npm run i18n:stamp` and checked by `tests/integration/i18n-catalog-parity.test.ts` in `npm run test:docs`. A missing key in a non-default locale **throws at build** — never a silent English fallback. **No i18n runtime dependency** (~100 lines in `src/i18n/t.ts`); plurals are not needed for Tier A and `Intl.PluralRules` is the recorded path when a Tier B tool needs them.
6. **Links**: `localizedHref(path, locale)` prefixes only registry (Tier A) routes; every other path is returned unchanged, so a Spanish page links to the English tool rather than a `/es/…` 404, and pairs it with the `common.notice.contentInEnglish` line. The switcher targets the same path in the other locale and falls back to that locale's home when the page is not in the registry (hand-off §3 rule, a deviation from the stanza's "list only locales the page exists in").
7. **SEO**: `<html lang>` from the registry; canonical is always the page's own locale URL; `hreflang` for every live alternate plus `x-default` → English, emitted only when the route exists in ≥2 live locales; `og:locale` + `og:locale:alternate`; BreadcrumbList names and item URLs in the page locale via `slugToName(slug, locale)`, whose English map is now derived from `en/common.json`; `inLanguage` on the ProfessionalService node. The sitemap's `i18n` alternates come from the same registry; the filter strips the locale prefix before matching exclusions and drops draft-locale URLs.
8. **Persistence** is `localStorage.gstLang` (the locale code), written by the switcher and the first-visit band, read only to suppress the band. **No cookie, no auto-redirect, no geolocation.** Suggestion source is `navigator.languages` through `resolveLocale`.
9. **Analytics**: `trackEvent` attaches `locale` (from `document.documentElement.lang`) to every GA4 event; event names, labels and destinations stay English.
10. **Formatting**: `src/i18n/formatters.ts` wraps `Intl.DateTimeFormat`/`NumberFormat` and takes a registry locale or a bare tag (client scripts pass `document.documentElement.lang`). Currency is a caller argument, never inferred from the locale (hand-off §4); the hub-tool currency control is Tier B and not built here.
11. **404/500 stay English** with a trilingual hint line — accepted deviation from the stanza's Tier A list, because the platform cannot know a locale for a static error page.
12. **Names**: the registry is `locales.ts` (plural), not the stanza's `locale.ts`, because it exports the set and the helpers over it.
13. **The Spanish is Colombian; the locale is still `es`** (operator decision, 2026-09-05). The catalogs are written in the Colombian business register (LOCALIZATION.md § Translation workflow lists the lexical choices) and `intl` / `ogLocale` carry the region (`es-CO`, `es_CO`) so dates, numbers and Open Graph agree with the copy. The code, URL prefix and switcher name stay bare (`es`, `/es/`, `Español`) because the site offers one Spanish, not a dialect set; an `es-MX` or `es-ES` row would be the dialect case decision 1 already covers. For the same reason the Portuguese URL prefix is `/pt/`, not `/pt-br/` (changed 2026-09-05 before any `/pt-br/` URL was published, so nothing redirects): every prefix is the bare language, and the code `pt-BR` keeps carrying the region for `<html lang>`, hreflang and `Intl`. A second Portuguese would claim `/pt-pt/` and this row would keep `/pt/`. Likewise the Portuguese row is named `Português`, not `Português (Brasil)`: the region qualifier told the menu's widest row something it did not need to know.

**Rejected**: an i18n library (`astro-i18next`, `paraglide`) — the site has no plurals, no ICU needs, and a dependency would own the type story this repo already gets from JSON imports; per-language duplicate pages — 8 Tier A pages × 3 locales of drifting markup; a `fallback: 'rewrite'` so `/es/` could ship partial — duplicate content; cookie-based preference — would drag BL-001 (consent) into scope; IP geolocation — wrong for travellers and VPNs, and `navigator.languages` is the user's stated preference; folding region into `gstLang` — conflates two axes the hand-off keeps separate.

## Consequences

- **Cites this ADR**: `astro.config.mjs` (i18n + sitemap config), `src/i18n/locales.ts`, `src/i18n/routes.ts`, `src/i18n/t.ts`, `src/components/SEO.astro`, `src/utils/sitemap-filter.ts`, `src/pages/[locale]/[...route].astro`, `src/page-templates/registry.ts`, `tests/unit/i18n-locale.test.ts`, `tests/integration/i18n-catalog-parity.test.ts`, `tests/unit/i18n-no-stray-literals.test.ts`.
- **Adding a locale** is one registry row plus catalogs plus sidecars; the resolver, routing, sitemap, hreflang, breadcrumbs, switcher and band all read the registry. `tests/unit/i18n-no-stray-literals.test.ts` fails on any locale literal typed outside `src/i18n/`.
- **Going live** is a one-word change (`status: 'live'`) gated by the checklist in LOCALIZATION.md; nothing else moves.
- **Accepted trade-offs**: draft pages are publicly reachable (by design, for review) and `noindex`; English-only routes linked from a localized page carry a notice rather than a translation; the `process.env` exception in `locales.ts`; the E2E localization spec reads liveness from the registry, so parking a live locale as `draft` fails its first test by name (a **second**, forced-live dev server on 4326 was tried and removed the same day — two cold Vite servers sharing `node_modules/.vite` in CI produced `504 Outdated Optimize Dep` on another spec's dynamic import; DEVELOPER_TOOLING § localization spec) — and the Playwright server runs with `ASTRO_DEV_BACKGROUND=0`, because Astro 7 daemonizes `astro dev` outside CI and Playwright reads the parent's exit as a crash (DEVELOPER_TOOLING § Common workflows).
- **The announcement sash renders in every locale** (revised 2026-09-05 after the first cut hid it off English and the operator saw the banner "disappear" on `/es/`): the registry stays English and structural, `src/i18n/<locale>/announcements.json` carries the copy, `localizeAnnouncement` overlays it and localizes Tier A hrefs. The English catalog mirrors the registry under a unit test, so English still has one source.
- **Spanish header labels** were the widest row: `nav.about` is `Equipo` (six characters) rather than `Nosotros`, and with the switcher present the ≤400px tier drops the links' tracking to 0, so Spanish holds one row from 360px like English (measured; breadcrumb and page copy keep `Nosotros`).
- **Measured with the fifth nav item** (Chromium, 2026-09-05): the header row needs 318px and holds one line from a 350px viewport, wrapping under the logo below that through `Header.astro`'s pre-existing ≤400px safety net with zero horizontal overflow; the sash reserve tiers are untouched. The hand-off's 36px/32px trigger height is the existing header density, deliberately below `--touch-target-min`, while every menu row and mobile band button clears it.
- **Text expansion, measured 2026-10-01** (Chromium; every Tier A route × en/es/pt × 1280/768/480/360 plus the first-visit band, 144 loads; then the trial page's hidden states — issued, re-issued, code flow and every error kind — at 360/480, 48 more): zero horizontal page overflow anywhere. One defect, fixed: the trial page's h1 was `nowrap` + ellipsis and cut the Portuguese title at 480px ("…POR 3…") and every locale at 360px; it now wraps, pinned in `tests/e2e/hub-mcp-trial.test.ts`. One accepted by the operator as designed: the breadcrumb's current crumb ellipsizes in es/pt at 360px on the trial and from-code pages, where the h1 names the page in full. `hyphens: auto` is deliberately **not** enabled — STYLES_GUIDE § Text expansion prefers `overflow-wrap: anywhere`, because the mono face has no hyphenation-friendly metrics. The announcement sash's localized ink containment is pinned by `localization.test.ts` whenever an entry is live.
- **Revisit triggers**: a first dialect (validate the language-step ordering: "prefer the locale whose code IS the language" then registry order); a region preference (new key, formatters gain a region argument); a Tier B tool needing plurals (`Intl.PluralRules` in `t.ts`); Vercel gaining per-locale error pages (revisit decision 11); a locale whose organic search matters enough to want translated slugs (the route table is keyed by route `id`, so a per-locale path column can be added without touching pages — decision 2); a locale whose direct-traffic share is large enough that the first-visit band's friction shows in GA4 (the only case for reconsidering automatic redirects — decision 8). The last two were stated in the BL-153 stanza and recorded here on 2026-09-27.

## Amendment — 2026-10-24 (BL-153 Slice 3): Tier B routes and the display currency

TechPar (`/hub/tools/techpar/`) is the first hub tool served in every locale. What that settled:

1. **Tier B is a second registry list, not a tier field.** `src/i18n/routes.ts` gains `TIER_B_ROUTES` and `LOCALIZED_ROUTES = [...TIER_A_ROUTES, ...TIER_B_ROUTES]`; `localizedHref`, `isLocalizedRoute`, `alternatesFor` and the catch-all read `LOCALIZED_ROUTES`, so the switcher, band, hreflang, breadcrumbs and sitemap follow without further change. `TIER_A_ROUTES` keeps its meaning (the launch set). **Consequence for decision 2's launch rule:** the catch-all builds every locale × `LOCALIZED_ROUTES` and the parity guard requires every namespace in every locale, so a **new** locale must now carry the Tier B catalogs as well — "launches whole" means Tier A plus whatever Tier B is registered when it launches.
2. **Tier B publishes machine-translated, review owed** (operator decision 2026-10-24), as Tier A did on 2026-09-05. This overrides BACKLOG BL-153's "machine-only translation ships to no locale" for Tier B; the owed review is a row in LOCALIZATION.md § Draft → live.
3. **Tool scripts get their strings from one JSON island per page** (`<script type="application/json" data-techpar-strings>`), parsed lazily by a per-tool `strings.ts` that falls back to the static English catalog when no island exists (unit tests import the scripts under jsdom). Scripts never import `t.ts` — its eager glob would ship every catalog to the browser; `{name}` filling is the shared `src/i18n/interpolate.ts`. Content modules a script alone reads (TechPar's signal copy and recommendations) move into the catalog; content the engine or the MCP server also emits (TechPar's stage labels and notes, its category and zone names) stays English in code and is translated at render by key, with a unit test pinning the English catalog to the code.
4. **Currency is a display unit, never a conversion, and defaults to USD in every locale.** This is decision 10 as written — currency is never inferred from the language. Hand-off §4 says both "never inferred from language" (its overview) and "default follows locale (pt-BR→BRL …)" (its §4); the first is adopted because it is the language/region split this ADR exists to keep, and because a locale-dependent default would make a missing currency in a shared link or saved state mean different things on `/` and `/pt/`. The visitor's choice persists per tool: TechPar in its URL and saved state (`u`), the Tech Debt Calculator in its URL only (`cur`, beside `s` — a stored preference would relabel an `s`-only MCP deeplink in the reader's currency). The codes live in `src/i18n/currency.ts`; every read goes through its allowlist, because the value is painted into the page (an unvalidated `?u=` was an injection path until this change). The Tech Debt Calculator's fixed-rate conversion was removed under the same rule.
5. **Money keeps the tools' short shape.** `formatMoneyShort` reproduces TechPar's `formatDollars` thresholds and rounding (`$1.6M`, `$500K`), so English output is byte-identical, and takes only the decimal separator from the page language (`R$1,6M`); the symbol is a fixed per-code table (`R$`, `C$`, `A$`) and the K/M/B suffix stays in every language. `Intl` compact notation was measured and rejected: it drops the `.0` (`$1M`), spells CAD `CA$`, and in es-CO prints `US$2500 M` and mixes `K`/`k`. Percentages and other numbers use `formatters.ts` with the page language; analytics payloads stay dot-decimal.
6. **Hand-off §4 control placement — deviation.** TechPar keeps its currency control in the Profile panel, in the page's own `.tp-seg` style, rather than as a `.brutal-segmented` in the action bar: TechPar's action bars exist only on the Analysis and Trajectory tabs, after the amounts are entered, and one `.brutal-segmented` among the panel's `.tp-seg` groups would mix two active-state styles. The Tech Debt Calculator keeps its `<select>` in its action bar.

**Text expansion, measured 2026-10-24** (Chromium; TechPar × en/es/pt × 1280/768/480/360 × light/dark, walked through every tab and the hidden states — empty states, a filled PE profile with two historical years, deep-dive costs with the sanity and period warnings, baseline, three saved scenarios, the open methodology, the chart): zero horizontal page overflow and no clipped text after two fixes. The six-button currency group (BRL is the sixth) clipped AUD inside the 320px `.tp-seg` at every width, so it takes the existing `tp-seg--wide` variant the Industry group uses (440px; wraps under 768px). The scenario comparison table, about 550px wide with three scenarios, pushed every locale's page sideways under ~560px — English included, so it predates this change — and now scrolls inside its own box.

**2026-10-26 — the Tech Debt Calculator joins Tier B**, on the same rules. Three refinements came with it:

- **One island reader.** The per-tool `strings.ts` is now a two-line binding of `createToolStrings({ en, prefixes, selector })` in `src/scripts/tool-strings.ts`, so a third tool adds no copy of the parser.
- **Typed amounts follow the page language.** The calculator's direct inputs show money in the page's short form (`R$1,2M` on `/pt/`), so a reader there types a decimal comma. Its `normalizeLocaleAmount` reads, in a comma-decimal language, exactly one `,` as the decimal point and a `.` before exactly three digits as grouping; more than one `,` can only be English-style grouping (`1,000,000`), so that input passes through and reads as English. English input is untouched, and the engine's parser is unchanged.
- **Tool numbers use `htmlLang` on both sides — a refinement of decision 13.** Decision 13 has `Intl` read the registry's `intl` tag (`es-CO`). A client script only has `<html lang>` (`es`), so the tool templates format their first paint with `htmlLang` too, and server and client agree. The two tags differ only in grouping a bare four-digit number (`1234,5` vs `1.234,5`), which no tool prints: money is suffixed, and percentages and counts stay under 1,000.

The engine's burden levels, shared-link field labels and copy-summary lines gained keys and optional localization hooks (`BurdenKey`, `STATE_FIELD_LABELS`, `buildSummaryText` options) whose defaults print what the MCP server always printed. The deployment-frequency labels and DORA tiers stay English in `DEPLOY_OPTIONS`, because they are the `estimate_tech_debt_cost` enum, and the page translates them by index.

**2026-10-26 — Infrastructure Cost Governance joins Tier B**, and settles the revisit trigger below for ICG: its MCP-shared content is **translated at render by key**, not split from the MCP's copy. The domains, questions and recommendations stay in the TypeScript data the Worker imports; the English catalog mirrors them by id and a unit test pins the two, and the page renders each by id. Two further rules came with it:

- **Page-only copy leaves the Worker-deployed engine.** `buildSummaryText` and `contextualizeScore` produced English the MCP server never emits; they moved from `src/utils/icg-engine.ts` to the page's `logic.ts` (ADR-0042), with full-text snapshots proving the English output byte-identical. A later tool should do the same rather than add localization hooks to an engine for copy only the page shows.
- **The first plurals.** Counts use `pluralKey` (`Intl.PluralRules`, folding every category English lacks into `other`, so each locale carries `one` and `other`); lists use `formatList` (`Intl.ListFormat`), which keeps the English page's own joiner.

**2026-10-27 — the Diligence Machine joins Tier B**, and settles the revisit trigger below for the last named tool: translated at render by key, as ICG. Its questions, attention areas and topics stay English in the data the Worker imports; the English catalog mirrors them by id in a namespace of their own, `diligence-machine-data`, which the client never imports (the script falls back to the bundled data, so the English page ships the prose once), and a unit test pins it to the data. The wizard's labels, which only the page shows, moved out of `wizard-config.ts` into the `diligence-machine` catalog; the file keeps the `*_IDS` the MCP schema imports. Trigger tags reuse the target-parameters labels (`js.meta.*`), pinned equal to the engine's `CONDITION_LABELS`, so one translation serves both.

**Revisit triggers added**: a reader asks for native compact suffixes (`R$ 1,6 mi`, `US$ 1,6 M`) — the K/M/B suffix was chosen for consistency and stable tests, and is a one-function change in `currency.ts`; a second Tier B tool whose content the MCP server also emits (ICG, Diligence Machine) — decide per tool whether its content is split from the MCP's English copy or translated at render by key (settled for both: translated at render by key, 2026-10-26 and 2026-10-27).
